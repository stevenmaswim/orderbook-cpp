## Workloads

- **py_parity**: the Python engine's own benchmark op stream, recorded by `bench/py_parity/export_trace.py` running `demo.trader` unchanged (seeds 42, 43, 44, single-threaded) against the Python engine at commit a7e19ca. 13,811 ops = 12,000 submits (90% limit over a 101-tick band, 10% market, qty 1..100) + 1,811 cancels. `bench/py_parity/py_parity.bin`, sha256 `8f7bc6e745150071...`. One run = 200 back-to-back replays, each on a fresh book (throughput) or 20 (latency).
- **shape**: the same distributions generated in C++ (`bench/workloads.hpp`), 1,000,000 submits, seed 1. One replay per run.
- **wide**: the shape workload with prices spread over the whole 20,000-tick band instead of 101 ticks, so the book is sparse. Same size and seed.

Every book's end state on py_parity (trades, traded qty, resting orders, every price level's qty) matched the Python engine's recorded end state, and all books matched each other on shape and wide. The script refuses to write this file otherwise.

## Gateway thread to matcher thread through the SPSC ring (upgrade E)

`bench/pipeline_main.cpp`, `pool_array` book, shape workload. A gateway thread stamps each op and pushes it into a 16,384-slot ring; a matcher thread pops it, applies it, and records done time minus stamp. *direct* is the same ops on one thread with no ring (timer around each call). *saturated*: the gateway pushes as fast as it can. *paced*: one op per microsecond, so the ring stays nearly empty. *padded* keeps the two threads' indices on separate 128-byte lines; *unpadded* packs them onto one line on purpose (false sharing).

| Mode | Ring | ops/sec | p50 ns | p99 ns | p99.9 ns | max ns |
|---|---|---:|---:|---:|---:|---:|
| direct | none | 21,056,135 | 41 | 125 | 208 | 304,750 |
| saturated | padded | 9,798,393 | 1,645,000 | 2,063,292 | 2,237,917 | 2,264,958 |
| saturated | unpadded | 7,854,610 | 2,094,792 | 2,638,542 | 2,705,083 | 2,779,917 |
| paced | padded | 1,000,001 | 250 | 26,209 | 144,833 | 437,875 |
| paced | unpadded | 1,000,001 | 292 | 33,375 | 160,375 | 477,833 |

How to read it: the ring does not make matching faster. Saturated pipeline throughput is below direct calls on one thread, because every op now also crosses cores. Saturated latency is almost all waiting in a full queue (about ring size x time per op), so it measures queueing, not the handoff. The paced rows are the handoff-plus-match cost. Both matcher and gateway busy-spin; with no hard core pinning on macOS, tail values include the OS descheduling a spinning thread.

## NASDAQ TotalView-ITCH 5.0 replay (upgrade G)

Input: the first 64 MB of the gzip of `https://emi.nasdaq.com/ITCH/Nasdaq%20ITCH/01302019.NASDAQ_ITCH50.gz`, decompressed: 166,068,224 bytes, sha256 `25aec810253139a3...` (fetch with `tools/fetch_itch_sample.sh`; not committed). This is the start of the trading day's feed, mostly pre-market. `bench/itch_main.cpp` reads the file into memory first, then parses each length-prefixed message and applies adds (A, F), executions (E, C), cancels (X), deletes (D) and replaces (U) to one `intrusive_map` book per stock locate. Trades against hidden orders (P) and all other types are counted only.

ITCH is the exchange's own output: replaying it exercises the book's data structures (ladder, FIFO levels, id index), not this engine's matching, because the feed already says what matched.

## What this does not measure

- One thread, one instrument, in-process calls: no network, no parsing, no queueing.
- The throughput tables above are single-threaded matching speed. No thread count produced them; the pipeline section is the only two-thread measurement.
- macOS cannot hard-pin a thread to a core; the QoS hint above is all that was applied.
